# WORKFLOW.md · 多 agent 公共协作方案

> 本文档定义所有 agent 与人类的**协作流程**：认领任务、走评审门、写交接日志前必读。它是这套文档系统的核心；任何流程动作与本文件冲突时，停下来先对齐本文件。

## 角色定义

| 角色 | 职责 | 约束 |
|---|---|---|
| 起草 agent | 写模块文档的需求段、技术调研段、技术方案段、任务清单段 | 不施工自己起草的模块（可同工具不同会话） |
| 施工 agent | 按任务清单施工，小步提交 | 一次只认领一个任务；不验收自己施工的模块 |
| 验收 agent | 对照 EARS 验收标准逐条核验，写验收段 | 必须与施工 agent 是不同会话/工具 |
| **Simon**（人类评审者） | 三个评审门（需求/技术/验收）的**唯一批准人**；所有 approve/reject 决策 | agent 不得代为批准 |

三类 agent 只是角色，同一工具的不同会话可分别担任；关键纪律是**生成与评审分离**。

## 模块生命周期六步

每个模块按此顺序推进，状态实时登记在 [ROADMAP.md](ROADMAP.md) 看板：

1. **需求评审**（`未起草 → 需求评审中 → 需求冻结`）
   起草 agent 复制 [modules/README.md](modules/README.md) 模板建 `docs/modules/Mxx-slug.md`，填写需求段：用户故事 + **EARS 验收标准**（`WHEN <触发> THE SYSTEM SHALL <行为>`，每条可测试）+ **显式列出模糊点清单**。提交 Simon 批准 → 需求冻结。拒绝即中止返工，不带着疑问进入下一步。
2. **技术调研**
   起草 agent 写技术调研段：候选方案对比 + 结论 + 风险，引用 `deliverables/research/` 底稿作为论据，不凭记忆选型。
3. **技术评审**（`需求冻结 → 技术评审中 → 就绪(契约冻结)`）
   写技术方案段：接口契约（落到 packages/shared 的 Zod schema 变更）+ 改动文件清单 + 数据模型影响。Simon 批准 → 契约冻结。**重大取舍必须同时提 ADR**（见 [adr/0000-adr-convention.md](adr/0000-adr-convention.md)）。
4. **任务拆解**
   写任务清单段：每任务带 DoD（Definition of Done）+ 依赖 + 影响文件。任务粒度 = 一个会话能完成并留下 clean state。
5. **认领施工**（`就绪 → 施工中`）
   在 [ROADMAP.md](ROADMAP.md) **原子认领**（一次编辑同时写入状态+认领人），一次一个。开工前固定三步：读 [PROGRESS.md](PROGRESS.md) → 看 `git log` → 跑冒烟（安装+启动+已有测试）确认环境没被上次留坏。
6. **验收合并**（`施工中 → 待验收 → 完成`）
   验收 agent 对照 EARS 逐条核验并在模块文档验收段记录结果，Simon 做最终决策。小步合入主干，不搞长寿功能分支。

## 防卡死九条规则

1. **契约先行**：packages/shared 接口冻结后才放开并行施工。
2. **mock 不等人**：下游模块用冻结契约的 mock 实现先行，不等上游真实实现。
3. **blocked 是一等状态 + 时间盒**：同一问题尝试 2–3 次不通，立即转 blocked——在 ROADMAP 看板写明阻塞原因与所需输入（谁、给什么），不许闷头死磕。
4. **认领即锁定文件范围**：任务的影响文件清单即所有权边界，越界改动必须先沟通。
5. **主分支永远可运行**：任何时刻 `pnpm install && 启动 && 测试` 必须全绿。
6. **会话结束留 clean state**：做不完的半截功能先收尾，或在 PROGRESS.md 写明恢复路径（哪个文件改到哪、下一步做什么）。
7. **生成与评审分离**：施工者不验收自己的模块；DoD 由任务清单定义，不由施工 agent 自评。
8. **测试棘轮**：永不删除或弱化已有测试；覆盖率/断言只能增不能减。
9. **依赖完成自动解锁**：认领任务前先检查看板中依赖模块是否已到"就绪(契约冻结)"；依赖完成即解锁，无需额外协调。

## 并行规则

- **同 Wave 模块可并行**施工；跨 Wave 看依赖（见 [MODULES.md](MODULES.md) 五波总览）。
- 跨模块通信**只允许**通过 packages/shared 已冻结契约；禁止 import 其他模块的内部实现。
- **文件所有权边界 = 模块边界**：每个施工 agent 只动自己任务清单列出的文件；packages/shared 的变更只能发生在技术评审之后。

## PROGRESS.md 写作规范

- **append-only**：只追加，不改历史；最新日志在最上方（倒序）。
- **叙事式**，不是数据转储。每条包含四要素：
  1. 现在什么最重要（当前焦点）
  2. 本会话做了什么 + 验证结果（跑了什么命令、什么绿了/红了）
  3. 下一步是什么（具体到"谁、做哪个模块的哪一步"）
  4. 坑与教训（给下一位失忆工程师的提醒）
- **每会话结束必写**，同时更新 ROADMAP 看板状态。

## ADR 规范

- Nygard 五段式：Title / Status / Context / Decision / Consequences。
- 存于 `docs/adr/`，命名 `NNNN-kebab-case.md` 顺序编号。
- **只增不改**：变更决策用新 ADR supersede 旧条目，旧条目标注被谁取代。
- 细则见 [adr/0000-adr-convention.md](adr/0000-adr-convention.md)。
