# 上下文与设备验证成本管理

更新：2026-09-17。此页是项目方法的**唯一详细来源**；根目录 `AGENTS.md` 只保留入口和不可违反的边界，项目 Skill 负责按任务调用本页。成本控制不能削减用户明确要求的验证、既定测试棘轮或必要的安全/准确性检查。

## 本次审计

原冷启动链会顺序读 `AGENTS`、`CONTEXT`、`ARCHITECTURE`、`ROADMAP`、`WORKFLOW`、`PROGRESS`、`HANDOFF`，当前合计约 **97 KB**；其中 `PROGRESS.md` 一份已达约 **56 KB / 400 多行**。`HANDOFF.md` 仍描述 M03–M17 尚未施工，与 ROADMAP 的 M01–M06 进度相反。全量读取不只费上下文，还会把历史状态误当作最新事实。已把 HANDOFF 改为静态导航；PROGRESS 历史不改写。

| 信息 | 唯一事实源 | 其他地方如何写 |

## 按任务取上下文

1. 进入项目先读 `AGENTS.md`，看 `git status --short --branch`、最近 1–3 个提交，以及 `PROGRESS.md` **最新一条**。若有并行未提交文件，先划文件范围，不覆盖他人工作。根 AGENTS 是稳定约束；动态状态留在 ROADMAP/PROGRESS，避免每个阶段都改入口。
2. 按问题定位：`rg -n '关键词' docs apps packages` → `sed -n '起,止p' 文件`。看文件清单用 `rg --files`。先路径/命中行，再相邻片段；不默认 `cat docs/*.md` 或整个页面树。
3. 做 UI 时读 `CONTEXT` 的相关 token/设计段和对应组件、模块文档；改存储/契约时读 `ARCHITECTURE` 的相关红线、shared schema 和对应模块；改变状态/评审门时读 `WORKFLOW` 与 `ROADMAP`。设备调试只读设备速查，遇到安装问题才开完整版。
4. 长会话在里程碑后保留精确的「已完成、变更文件、验证、未决、下一动作」交接摘要；不要重新塞入全文日志。跨会话从 Git diff、最新 PROGRESS、相关模块重建事实，不依赖聊天记忆。
5. 修改事实时只改其权威文件，并更新必要的索引链接。新的调研应以日期、来源、结论、失效条件收束；若与现有文档重复，优先合并或替换过期入口。每次新增 Skill 前检查能否扩展已有 Skill。

## 操作成本分级与退出条件

这些是**选择证据的顺序**，不是禁止必要验证，也不是要求用户再授权。已经获得的任务授权继续有效。

| 层级 | 典型操作 | 何时升级 |
|---|---|---|
轻 | `rg`、局部文件、Git diff、纯函数/定向测试、静态配置检查 | 能回答问题即停止；不要为“保险”重复全仓扫描 |
中 | 已运行的 Metro / 浏览器预览、现有模拟器的单条目标路径、一次关键截图 | 有布局、导航、动画或平台行为必须观察时；复用已有设备和构建，不盲目重启 |
重 | 首次/变更原生配置后的整包编译、真机操作、长串 UI 自动化、录屏、反复截图、EAS 云构建 | 先写待证伪假设、目标设备、最短步骤和通过/失败信号；保留日志/截图路径。一个路径验证完后才决定是否扩大矩阵 |

典型闭环：先静态定位 → 一个最小复现 → 一次目标平台验证 → 修正 → 必要的双端回归。原生依赖或配置没变时复用开发版，只让 Metro 刷新；已有截图/日志能说明同一状态时直接复用。需要完整 iOS/Android 验收时照做，不以“省 token”为由降低验收范围。报告必须区分“代码检查通过”“模拟器观察到”“真机观察到”。

电脑操作/截图的高成本不只在模型 token，也包括图像输入、工具调用、构建分钟数和人的等待。优先用目的明确的 CLI/API 获取状态（例如 `simctl`、`adb`、`xcodebuild` 的限量输出），只有视觉判断或必须点 UI 时才调用电脑控制工具；图片只截关键转折，避免循环抓全屏。若第一次重试仍是同一失败，先读错误和环境状态，不直接重复完整编译。

## 缓存与观测

OpenAI 官方说明提示缓存依赖**完整前缀匹配**，工具定义、指令、历史上下文与模型设置的变化都可能降低命中；技能按名称/描述发现、使用时才加载全文。故本项目把稳定规则留在短 AGENTS/Skill，动态进度留在按需文档；读工具输出时限制范围，优先同任务内复用已读证据。**这能降低无用输入和提高复用机会，但不能保证 Codex 桌面端的实际缓存命中。** API 的 `prompt_cache_key` / breakpoint 等参数也不应被臆造为本地仓库配置。

评估优化前后至少记录：每次任务读取的文件数和输出量、重复读取次数、原生构建次数、截图/录屏次数、任务耗时和漏检/返工情况。若运行环境提供真实 `cached_tokens`、`cache_write_tokens`，再比较命中与总成本；若没有，只报告上述**代理指标**，不宣称节省了某个百分比 token。较短输入也可能比缓存命中率更重要，不能为凑缓存阈值故意灌入无关文档。
